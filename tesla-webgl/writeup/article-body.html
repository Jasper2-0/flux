TESLA

sunflower, july 2000 → javascript / webgl2, 2026

How a Windows demo from the year 2000 was brought to the browser: reverse-engineering its data archive, replaying its fixed-function OpenGL habits on WebGL2, and re-timing eleven effects against the soundtrack. Every viewer on this page runs the actual engine of the port against the actual data files of the original release — scrub them, x-ray them, and watch their draw calls.

01

The patient on the table

Tesla was released by the Polish/Nordic group Sunflower in July 2000 — a Win32 demo on OpenGL, from the era when a readme could brag that a Voodoo card “won’t cut it because the demo uses some textures larger than 256×256.” The release is three files: tesla.exe, a 3.4 MB archive called data.pak, and the soundtrack tournesol.mp3. The group also published the C++ source, which is what made a faithful port possible instead of a remake.

The architecture is pleasantly blunt. There is an effect manager holding up to 64 effects, each with a start and end time in seconds. Every frame it walks the list and calls Do(time) on whichever effects are live. No scene graph, no scripting, no message bus — the soundtrack is the conductor and wall-clock time is the score. The entire show is eleven AddEffect calls. That timing table, copied digit for digit, is the spine of the port; everything else hangs off it.

Two details of the original build tell you a lot about its year: the main loop has a built-in AVI recorder (frame-by-frame glReadPixels into a Video-for-Windows compressor — how demos got captured before screen recording was easy), and the effects freely mix per-frame CPU vertex math with immediate-mode OpenGL. The whole demo never once uses hardware lighting: every surface is either textured, alpha-blended, or both.

02

Cracking data.pak

The release only ships data.pak, and the source’s archive reader wasn’t included. Opening the file in a hex viewer gives it away immediately: it starts with 4D 4D — the magic of a 3DS mesh file. So the pak stores its files as raw, uncompressed blobs back to back, which means the directory must live at the end. And it does: the last four bytes are a pointer to a directory of [offset, size, reserved, nameLen, name] records with DOS-style paths like DATA\TEXTURES\SPHERE.JPG. 

offset 0x36B317 ← tail pointer (last 4 bytes of file)
  u32 count = 22
  entry: u32 offset · u32 size · u32 0 · u32 nameLen · char name[nameLen]

The port fetches the pak once and parses this directory in about forty lines of JavaScript — the browser build you’re reading this on did exactly that a moment ago. Below is the live directory, decoded from the real archive embedded in this page, with every texture thumbnailed by the same decoders the demo uses (browser-native JPEG/PNG, plus a hand-written TGA reader that flips rows and swizzles BGRA, just like the original’s image library). Click any tile to enlarge.

A fun archaeology detail: the source references two textures — scape.jpg and spheresmall.png — that are not in the shipped pak at all. They belong to effects that were cut or re-textured before the party version. The port only loads what the timeline actually uses.

03

Reading the meshes

Three 3DS files drive the geometry effects: meta.3ds (six blobby morph targets), faces.3ds (four heads), and kbuu2.3ds (the “tree”). 3DS is a chunk format — a tree of [id, length] headers — and parsing it is the easy half. The hard half is reproducing the quirks of the loader the demo linked against, because the effects depend on every one of them:

  • Axis swap. 3DS is Z-up; the loader reads every vertex as (x, z, y) to make it Y-up.
  • UV flip. Texture V is stored as 1 − v on load.
  • Per-vertex collapse. 3DS UVs are per-face-corner, but the effects index UVs per vertex — last writer wins. The port collapses them the same way rather than “fixing” it.
  • Averaged normals. Vertex normals are the plain average of adjacent face normals — not re-normalized. The env-mapping passes feed on these directly, so their length matters.
  • Pivot space. The MATRIX chunk (read with the same axis shuffle, then inverted) maps world vertices into each object’s pivot space. The morphing effects lerp these pivot-space positions — skip this and the morph targets drift apart mid-blend.

The inspector below renders the parsed meshes as raw wireframes — no engine, just the parser’s output projected onto a 2D canvas. The morph slider does exactly what the demo’s morph effects do: linear interpolation between two objects’ vertex arrays with a cosine-eased parameter.

04

Faking fixed-function GL on WebGL2

The effects speak OpenGL 1.2: glBegin/glEnd, matrix stacks, glColor4f, blend modes, fog. None of that exists in WebGL. Instead of rewriting eleven effects against a modern API — and introducing eleven opportunities to change their look — the port implements a ~450-line emulation layer, minigl.js, so each effect could be translated almost line by line.

An audit of the original source showed the effects use a surprisingly small slice of GL: no lighting, no multitexture, one fog mode, five blend factor combinations, three matrix modes. Everything funnels into a single shader pair: 

// vertex                          // fragment
eye = uModelView * pos;            c = uUseVertexColor ? vColor : uColor;
gl_Position = uProjection * eye;   if (uTexEnabled) c *= texture(uSampler, vUV);
vUV = (uTexMatrix * uv).xy;        if (fog) c.rgb *= clamp((end - dist) / (end - start));
vEyeDist = -eye.z;
fixed-function habitport equivalent
glMatrixMode / glPushMatrix / glRotatef… CPU-side matrix stacks; the top of projection, modelview and texture stacks upload as uniforms per draw
glBegin(GL_QUADS) … glEnd() vertices buffered into one interleaved stream VBO; quads drawn via a pre-built shared index pattern
glVertexPointer + glDrawElements per-call upload of position/UV arrays (the effects rewrite them every frame anyway)
glColor4f before an array draw a uniform — not a constant vertex attribute; see the iOS section for why
GL_FOG, linear, black two lines in the fragment shader scaling RGB by eye distance
glGetFloatv(GL_MODELVIEW_MATRIX) read back from the CPU stack — the effects use it to build camera-facing billboards, via the demo’s own 4×3 affine inverse, ported verbatim

Two demo-era details survive in the port on purpose. The math library reproduces the original CMatrix memory layout and its hand-rolled affine inverse exactly — billboard orientation falls out of that code, and “close enough” math produces subtly wrong sprite orientations. And rand() is an MSVC-compatible LCG, so effects seeded by C-runtime randomness (flare streams, band spawns, the scanline flicker) draw from the same distribution the original did.

Every live viewer below shows the emulation layer’s debug counters: how many array draws, immediate-mode batches and vertices the active effect pushes per frame — and a wireframe switch that re-indexes every triangle as lines, which is the fastest way to see how cheap this geometry really is.

05

The eleven effects

Each effect is a stateless-ish object with one entry point: given the absolute time and its own start time, draw yourself. That design is why the port can scrub: rendering at t = 40 requires no replay of frames 0–39. The viewers below embed the real port — same classes, same data — with a scrubber, a play button, wireframe x-ray, and the draw-call HUD. Only one WebGL context exists on this page; it docks into whichever viewer you scroll to.

0:00–0:24 · SPINZOOM — the flicker intro

Eighteen copies of one textured quad, each rotated and scaled a little more than the last, drawn additively so they smear into a tunnel of light. The choreography lives in a keyframe envelope — a list of (time, brightness) pairs — and the envelope segment index doubles as a mode switch: segments 5–6 spin one way, 7–8 tumble fast, 9–10 breathe. Between blackouts, randomized dark scanline bands (CDarkQuads) flicker over everything — the effect this page’s viewers pay homage to.

This envelope is also where the iOS black-screen bug lived: the effect offsets its clock by −0.1 s, so the lookup must tolerate negative time. The plot’s playhead tracks the viewer.

brightness envelope unrTab: 0–24 s — the blackouts between pulses are authored, not rendered

The math. The tunnel is one matrix product iterated. Each of the 18 copies multiplies the current modelview by a small rotation and a near-unit scale, so copy i accumulates:

Mi = Mi−1 · R(axis, θ(t)) · S(s, s, 1),  s = 1.02 ⇒ copy i carries rotation i·θ and scale si (s18 ≈ 1.43×)

A geometric progression of scales with a constant angular offset is the recipe for a logarithmic spiral — the copies form an exponential tunnel whose walls are the same quad seen at 18 depths. Because blending is additive with α ≈ 0.23, regions where many copies overlap saturate toward white while the rim stays dim: brightness is effectively counting coverage. Try it below: steeper θ twists the spiral; s closer to 1 packs the copies tighter and brightens the core.

the transform cascade in 2D, additively composited like the effect — drag the sliders

0:24–0:48 · SHADEBALL — the title

A 13×13-segment sphere drawn twenty times, each copy evaluated at a slightly earlier time (t −= 0.014·(8 sin t + 12)) with a smaller scale and dimmer alpha — motion trails made of time travel rather than accumulation buffers. Front faces are culled so you look through each shell’s near side onto its far side, which is what gives the ball its X-ray glow. The TESLA lettering is simply a full-screen PNG composited over the top, faded by its own keyframe envelope.

title/ball alpha envelope — three pulses, hard zero crossings on the beat

The math. The sphere is the standard latitude/longitude parametrization; the interesting part is the sampling of time. Shell i is not a stored trail — it re-evaluates the same rotation formulas at a receding instant:

t0 = t,  ti+1 = ti − 0.014 · (8·sin t + 12) Δ ∈ [0.056, 0.28] s — the comb of samples stretches and squeezes with the music’s sway αi = 0.3 · (1 − i/12) · envelope(t)

Because the step size itself depends on sin t, the trail breathes: when the sine is low the 20 shells bunch into a tight afterimage, when high they fan out into long streaks. And note the alpha law: 1 − i/12 crosses zero at i = 12, so seven of the twenty shells are drawn with negative alpha — clamped to invisible. The original renders 35% more geometry than you can ever see; the port reproduces that faithfully (watch the vertices counter in the viewer).

the time comb, live — each tine is one shell’s sample time; height = its alpha; play the viewer above and watch the spacing breathe

0:48–1:07 · SPLINES — light writing

Sixteen trails, each a chain of 64 camera-facing billboards laid along a sum-of-sines path — a 3D Lissajous figure. The trail isn’t stored anywhere: sprite i just evaluates the same curve at t − 0.036i. The billboards face the camera via the inverted modelview matrix, and blend with SRC_COLOR, ONE — a self-multiplying additive mode that blows out to white where trails cross. Behind them, a cage of eight nested 600-unit spheres rotates in a second projection with a much wider field of view.

trail no. 0’s path, x/y projection, one 20-second window — the knots are where the additive blend flares

The math. Each coordinate of a trail’s center is a two-frequency sine sum — three incommensurate pairs make a curve that never repeats within the scene:

p(t) = A · ( sin(f1t) + sin(f2t + 1) ) per axis, with (f1, f2, A) different per axis sprite i samples p(t − 0.036·i) — the trail is time-shifted evaluation, no history buffer

The billboarding is the classic fixed-function trick. The modelview matrix V maps world to camera; its inverse maps camera axes back to world. So the first two columns of V−1 are “screen right” and “screen up” expressed in world coordinates, and a quad built as p ± 10bx ± 10by faces the camera exactly, no matter how the scene tumbles. For a pure rotation the inverse is just the transpose, but the demo runs its full 4×3 affine inverse — ported bit-for-bit, because this is the code that decides which way every sprite in the demo leans.

billboards from above: blue strokes are the sprites — whatever the camera angle, they lie along bₓ and stay face-on

1:07–1:27 · FFDENV + BANDS — the morph

Two effects overlap here, exactly as in the original timeline. The morph cycles through the six objects of meta.3ds in a ring, cosine-blending pivot-space vertices and normals. It renders twice per frame: a textured pass, then an additive environment-map pass whose UVs are the morphed normals rotated into camera space — 1999’s chrome, computed on the CPU. On top: Bands, forty ribbon trails flying at the camera, each new segment angled randomly off the last so the ribbons twist. Toggle the overlay off to study the morph alone.

The math. The morph is piecewise-linear in space but eased in time. With six targets on a two-second cadence:

cycle = 0.5·t,  A = ⌊cycle⌋ mod 6,  B = (A+1) mod 6 fT = cos((1 − frac)·π)/2 + 1/2 ← slope is zero at both ends v = (1 − fT)·vA + fT·vB,  n = (1 − fT)·nA + fT·nB

The cosine ease is what sells it: its derivative vanishes at the endpoints, so each shape rests for a beat before flowing into the next — linear interpolation would look like a machine part. Note the normals are lerped with the same weight and not re-normalized; their slight mid-blend shrinkage subtly dims the chrome at the halfway point, an accident of 1999 the port preserves.

The chrome itself is a sphere map: rotate the vertex normal into camera space, throw away z, and use (nₓ/2 + ½, ny/2 + ½) as texture coordinates. A normal facing the camera samples the texture center; grazing normals sample the rim — a poor man’s reflection that costs one matrix multiply per vertex.

left: the six-target morph ring, synced to the viewer above — right: the cosine ease vs. linear
sphere-mapping: each camera-space normal picks its texel by dropping z

Bands’ math is a constrained random walk. Each time the nearest segment scrolls past the near plane, the whole ribbon shifts down one slot and a fresh far-plane segment is spawned from the previous one:

anew = (aprev + U(−1, 1)) mod 2π,  r = 1 + 0.3·U(0,1) edge 0 = c + r·(sin a, cos a),  edge 1 = c + r·(sin(a + w), cos(a + w))

Both ribbon edges sit on the same circle, offset by the band’s width angle w — so the ribbon is a strip of chords whose orientation random-walks as it recedes. That’s the entire twist: no torsion math, just accumulated uniform noise wrapped mod 2π.

left: live far-plane cross-section, chords spawning as the walk drifts — right: the angle walk itself

1:27–2:25 · ENERGYSTREAM — the long haul

Fifty-eight seconds from one effect — a third of the demo. The trick is phased reconfiguration: a fan of sixteen (later eight) 600-unit textured planes rotates around the X axis while scrolling its UVs, and at hard-coded times the whole rig snaps 90° or 180° and swaps texture, reading as a scene change for free. Sixteen streams of 150 billboard flares race along the X axis with sine-wobbled Y/Z, wrapped by fmod into an endless river. This is the one effect that uses fog — linear, black, 200 to 500 units — to sink the plane fan’s far edge into darkness.

master alpha over the effect’s 58 s — each notch is a hard-coded phase snap (15 / 25 / 38 / 58 s)

The math. The flare river is a sawtooth: each of 2,400 flares advances linearly and wraps through fmod, with small per-flare sine wobbles decorrelating the lanes:

x(t) = fmod(x0 + v·m·t, 800) − 400 m snaps 1 → 2 → 2.5 at the phase times y(t) = y0 + 2·sin(7t + x0),  z(t) = z0 + 2·cos(7t + 3.14·i)

Seeding the phase with x0 is the elegant bit — position doubles as a random phase, so no extra state is stored per flare. The depth is handled by the demo’s only use of fog: a linear ramp that multiplies RGB by clamp((500 − d)/300). Under additive blending, black fog doesn’t “grey out” distant flares — it makes them contribute less light, which is exactly the right physics for glowing particles.

top: the fmod conveyor — flares exit right, re-enter left; bottom: the linear fog ramp that swallows them

2:25–2:45 · TUBES — the spline organ

The most engineering-heavy effect: a 6×8 grid of control nodes, wrapped into a cylinder, each node’s radius driven by two beating sine pulses. A Catmull-Rom patch tessellator subdivides every grid cell at render time — position, UV, color and normals all spline-interpolated — and the surface renders twice, UV-mapped and camera-space env-mapped. Around it, eight rigid textured cylinders spin at different rates. The seed sliders below change the tessellation density live — the original shipped locked at 4×6.

The math. Everything here rests on the Catmull-Rom spline: a cubic through four control values that passes exactly through the middle two. The demo’s kernel, in the arrangement it computes:

q(t) = fat³ + fbt² + fct + b fa = ½(3b + d − a − 3c),  fb = a + 2c − ½(5b + d),  fc = ½(c − a) q(0) = b,  q(1) = c,  q′(0) = (c−a)/2,  q′(1) = (d−b)/2 ← C¹ across segments

Because each segment’s end tangent equals the next segment’s start tangent, chained segments join with continuous velocity — that’s why the tube reads as one smooth organ rather than a stack of rings. The surface is the tensor-product version: for each patch, four column splines are evaluated, then those results feed a row spline — and not just positions: UVs, colors and env-normals ride the same interpolation. The tube’s shape is the radius field r(v) = pulse1(t·v) with a second pulse accumulating around each ring, which is why the cross-section spirals rather than merely bulging.

Play with the spline below — it uses the port’s exact kernel. The yellow ticks are the demo’s shipped tessellation density (6 samples per segment); the inset shows the four basis weights, including their negative lobes — the reason a Catmull-Rom curve can locally overshoot its control cage.

2:45–3:23 · POLKALIKE + TREE

Four tracks of 128 sprites stream toward the camera through a tunnel of rotating background quads. Each track’s spawn point traces a sum-of-sines curve that switches equations at 10 s and 20 s — the plot below shows all three phases. This is the demo’s only genuinely stateful effect: sprites integrate velocity frame by frame, so the port steps them on a fixed 60 Hz accumulator to stay speed-correct on any display. Twenty-one seconds in, the Tree fades up on top: the kbuu2.3ds mesh pushed through a 5×5×5 Catmull-Rom free-form-deformation lattice whose control points breathe with independent sine phases.

emitter paths, x/y plane — phase 1 (0–10 s), phase 2 (10–20 s), phase 3 (20 s+)
live 2D slice of the tree’s FFD lattice — the mesh is resampled through this grid every frame

PolkaLike’s math is forward integration plus a rotation basis. Each sprite advances p += v·Δt at a fixed Δt = 1/60, and builds its corners from a rotating orthogonal pair: with u = (cos a, sin a)·5 and u⊥ = (sin a, −cos a), the quad is p ± u ± u⊥ — a square spinning in the screen plane as it flies. Alpha is a pure depth ramp, α = −z/300 + 0.2, so sprites materialize out of the far darkness.

The Tree’s math is the demo’s heaviest per-vertex pipeline: free-form deformation through a 5×5×5 lattice. Each mesh vertex is expressed in normalized lattice coordinates, then re-interpolated through its 4×4×4 neighborhood of control points with tricubic Catmull-Rom:

(u,v,w) = (p − bboxmin) / cell lattice-space position 16 x-splines → 4 y-splines → 1 z-spline = 21 spline evaluations per vertex ≈ 1,700 verts × 21 ≈ 35k cubic evaluations per frame — on a 2000-era CPU

Because Catmull-Rom passes through its control points, an undeformed lattice reproduces the mesh exactly; every deviation of a control point bends all geometry in its 4-cell neighborhood, smoothly. 3:23–3:42 · FACEMORPH — the heads

The four heads of faces.3ds morph in the authored sequence 1 → 0 → 3 → 0, cosine-eased. Three passes per frame: two UV-textured passes whose texture matrices drift and counter-rotate against each other (the liquid surface shimmer), then the additive camera-space env pass that gives the bronze sheen. Depth testing is on and front faces are culled — one of only two places in the demo where the depth buffer matters at all. Behind the head, four of the tube cylinders return at increasing scales; over everything, a full-screen vignette PNG.

The math. The morph reuses the cosine-eased lerp from FFDEnv (sequence 1→0→3→0, period 2 s). What’s new is the use of the texture matrix as an animation channel. Each of the two skin passes transforms its UVs by a drifting rotation:

pass 1: uv′ = R(+30°·t) · uv + (0.05t, 0.10t) pass 2: uv′ = R(−20°·t) · uv + (0.05t, −0.05t)

Two copies of the surface texture sliding across each other at different angular velocities produce a beat pattern — the liquid-metal shimmer is literally moiré. The rotation rates differ by 50°/s, so the interference figure completes a cycle roughly every 7 seconds, which is why the skin never visibly repeats within the scene. The additive env pass on top uses the same sphere-mapping as FFDEnv, fed by the morphed normals — so highlights slide around the face as the identity changes.

the two UV lattices, synced to the viewer — the shimmer is their interference

3:42–4:14 · THING — credits

The comedown: eight big additive quads under a tilted camera, UVs drifting on independent sine phases, forming a slow aurora. The credit screens are full-frame PNGs cross-faded in a fixed schedule, and the scene opens with a pure white flash quad inherited from the previous effect’s final frame — a cut disguised as an exposure. When the envelope of the last credit reaches zero at 254 s, the demo simply stops calling effects. Roll credits, literally.

the three credit layers’ alphas across the outro — saffron → radix/lluvia → yoghurt

The aurora’s only mathematics is incommensurate phases: quad i drifts its UVs by sums like 0.4·sin(t + 6i) + 0.4·cos(2t + 4i) — eight quads, no two phase-locked, so the sheet of light never settles. A fitting last trick: the whole demo, reduced to its simplest ingredient — sines added to sines, drawn additively.

06

Clocks, seeds, and staying honest

The original started a hardware timer on the first frame and played the MP3 at the same instant, trusting the two never to drift over four minutes. The port inverts that dependency: the soundtrack is the clock. Every frame reads audio.currentTime, which makes sync survive tab throttling, dropped frames, and seeking — the arrow keys in the player literally just move the audio position and the picture follows.

Two things resist scrubbing. Effects that integrate state (PolkaLike’s sprite tracks, Bands’ ribbons) get fixed-step accumulators and are simply rebuilt when time jumps backward. And C-runtime randomness had to be replayed faithfully: the port implements the exact MSVC LCG (seed × 214013 + 2531011) so that, e.g., the sixteen flare streams scatter the way the original seeded them.

07

Getting it onto an iPhone

The port ran perfectly in desktop Chromium on the first full pass — and produced audio over a black screen on iOS Safari. That symptom was three separate bugs deep:

  • ImageBitmap uploads. The textures were decoded with createImageBitmap and handed to texImage2D — a path where WebKit has shipped black-texture bugs. Since every surface in the demo is textured, one bug blacked out the entire show. Fix: decode through a 2D canvas and upload raw RGBA bytes; identical everywhere, slightly slower, bulletproof.
  • Constant vertex attributes. Mesh draws set their color via vertexAttrib4f with the array disabled — historically unreliable on Safari’s Metal-backed WebGL. Fix: route the constant color through a uniform and a shader branch.
  • The real killer: a port bug hiding at t < 0.1 s. SpinZoom’s clock starts at −0.1 s; its envelope lookup ran off the end of the table and threw — on the very first frame, killing the render loop while the audio played on. Desktop testing never caught it because the harness rendered fixed mid-timeline stamps and never pressed play from zero.

The lasting fixes were procedural as much as technical: the render loop now sandboxes each effect (one crash shows a red diagnostic bar instead of eternal blackness), GL context loss and GL errors report themselves on screen, and the test harness gained a “press play and let it actually run from zero” test plus a sweep of every effect’s boundary timestamps — 36 edge cases that would have caught the crash instantly.

08

Testing a demo without eyes

The port was developed in a headless environment — no window, no GPU display, no speakers. Verification ran through Playwright driving headless Chromium on a software rasterizer: load the page, force the clock with a timeOverride hook, render, screenshot. Twenty timestamps across the timeline gave a filmstrip of every scene to eyeball against memory of the original; the boundary sweep and the play-from-zero test guard the edges numerically. The same timeOverride hook is what the viewers on this page use to scrub — the debugging affordance became the exhibit.
